Sample playing at the wrong speed or pitch? It’s a sample-rate mismatch

NoDAW Labs · Lacquer Vol. 06

When a sample plays a little too slow and flat, or too fast and sharp, it’s almost always a sample-rate mismatch: audio made at one rate is being played back at another without being converted. A 48 kHz file played at 44.1 kHz runs at 0.91875x speed and about 1.47 semitones flat. The other way round it runs 1.088x fast and 1.47 semitones sharp. Set the project rate, let the DAW convert the file instead of just playing it, and check the rate in the file’s header.

The loop sounded perfect in the pack preview. You drop it in, and something’s off. A little dark, a little lazy, not quite on the grid however you line it up. Or it’s the other way: brighter and pushier than you remember, with the vocal chop a touch chipmunky. The person who sent it swears it’s 140.

Or the beat is fine in the session, and then you put it under a video and by the second chorus the drums and the picture have drifted apart.

Same cause, most of the time. Nothing’s wrong with the audio. It’s being played on the wrong clock.

Why the rate changes the pitch

A WAV file is a long list of numbers plus a header that says how many of them make a second. Take one second of 48 kHz audio, 48,000 numbers, and play it at 44,100 per second, and that second takes longer to get through. Every wave is stretched, so every note is lower. Speed and pitch move together, exactly like a turntable at the wrong speed. That’s resampling-style varispeed, one of the three different jobs in resampling, pitch shifting and tempo change.

The arithmetic is just the ratio of the two rates. Here it is for the four common ones:

The one that bites is 44.1 against 48. The ratio is 1.08844, which is 146.7 cents, about a semitone and a half. That’s not a clean wrong key. It sits between notes, which is why it sounds “off” rather than obviously in the wrong key, and why your ear keeps trying to fix it with EQ. A 140 BPM loop turns into 128.62 or 152.38 BPM. A three-minute song gains 15.92 seconds or loses 14.63. Doubling a rate is a full octave, which nobody misses.

Against video the drift is easy to spot once you know to look: at 0.91875x the audio is 5.31 seconds behind after one minute and 21.22 seconds behind after four. If the sync looks right at the start and worse by the chorus, check the sample rate before you start nudging clips.

Where the mismatch sneaks in

  • Importing into a session at another rate. Some DAWs convert on import automatically, some ask, and some play the file as-is unless you tell them otherwise.
  • Samplers and older tools. Some load the raw sample data and play it at the engine’s rate, whatever the file says.
  • Mixed-rate sample packs. One folder, loops from three sources, two rates. The odd one out plays wrong next to the others.
  • The interface and the project disagree. On some setups the audio device can be set to one rate while the software expects another.
  • The header itself is wrong. A broken export or a bad edit writes the wrong number into the file. Now even a careful DAW plays it wrong, because it’s trusting the file.

Check what the file says

This script reads the rate straight out of the WAV header and tells you what happens if it plays in your session unconverted. Give it a note you know should be in the file, like a tuning tone, a held note or an 808 you know the key of, and it also checks whether the header is telling the truth:

#!/usr/bin/env python3
"""Read the sample rate a WAV file *says* it is (straight from the RIFF fmt chunk), and what happens
if it plays in your session without conversion. Optional: --expect-hz checks the strongest tone
against the pitch it should be, which catches files whose header itself is wrong.
  python3 rate_check.py --session 48000 [--bpm 140] [--expect-hz 440] *.wav"""
import argparse, math, struct, sys, numpy as np

def read_wav(path):
    with open(path, "rb") as fh:
        riff, _, wave_id = struct.unpack("<4sI4s", fh.read(12))
        if riff not in (b"RIFF", b"RF64") or wave_id != b"WAVE": sys.exit(f"{path}: not a WAV file")
        fmt = data = None
        while (hdr := fh.read(8)) and len(hdr) == 8:
            cid, size = struct.unpack("<4sI", hdr)
            if cid == b"fmt ": fmt = fh.read(size)
            elif cid == b"data": data = fh.read(size); break
            else: fh.seek(size, 1)
            if size % 2: fh.seek(1, 1)                   # chunks are word-aligned
    tag, ch, sr, _, _, bits = struct.unpack("<HHIIHH", fmt[:16])
    if tag == 0xFFFE: tag = struct.unpack("<H", fmt[24:26])[0]   # WAVE_FORMAT_EXTENSIBLE
    if tag == 3: x = np.frombuffer(data, f"<f{bits // 8}").astype(float)
    elif bits == 24:
        b = np.frombuffer(data[: len(data) // 3 * 3], np.uint8).reshape(-1, 3)
        x = (np.c_[np.zeros(len(b), np.uint8), b].copy().view("<i4").ravel() >> 8) / 2 ** 23
    else: x = np.frombuffer(data, {16: "<i2", 32: "<i4"}[bits]) / 2 ** (bits - 1)
    return sr, ch, bits, ("float" if tag == 3 else "PCM"), x.reshape(-1, ch).mean(axis=1)

def strongest_hz(x, sr):                                 # FFT peak, parabolic interpolation
    n = min(len(x), sr * 4); w = x[:n] * np.hanning(n)
    m = np.abs(np.fft.rfft(w, 4 * n)); k = int(np.argmax(m[1:])) + 1
    a, b, c = np.log(m[k - 1:k + 2] + 1e-20); k += 0.5 * (a - c) / (a - 2 * b + c)
    return k * sr / (4 * n)

ap = argparse.ArgumentParser(); ap.add_argument("files", nargs="+")
ap.add_argument("--session", type=int, required=True); ap.add_argument("--bpm", type=float)
ap.add_argument("--expect-hz", type=float); a = ap.parse_args()
def effect(r):                                           # speed ratio -> readable consequences
    return (f"x{r:.5f} speed, {12 * math.log2(r):+.3f} semitones" +
            (f", {a.bpm:g} BPM plays at {a.bpm * r:.2f}" if a.bpm else ""))

for f in a.files:
    sr, ch, bits, kind, x = read_wav(f)
    print(f"{f}: header says {sr} Hz, {ch} ch, {bits}-bit {kind}, {len(x)/sr:.3f} s")
    if a.expect_hz:
        hz = strongest_hz(x, sr); off = 1200 * math.log2(hz / a.expect_hz)
        print(f"  strongest tone at the header rate: {hz:.1f} Hz ({off:+.0f} cents vs {a.expect_hz:g})")
        if abs(off) > 50:                                # more than half a semitone: the header is lying
            true = round(sr * a.expect_hz / hz)
            print(f"  header looks wrong: the audio was made at about {true} Hz. Played by its header: "
                  f"{effect(sr / true)}\n  fix: re-stamp the header to {true} Hz (no resampling)")
            continue
    if sr == a.session: print("  matches the session: plays at the right speed")
    else:
        print(f"  unconverted in a {a.session} Hz session: {effect(a.session / sr)}, "
              f"lasts {len(x) / a.session:.3f} s\n  fix: convert it to {a.session} Hz (sample-rate conversion)")

The test files come from make_loops.py: two bars at 140 BPM, an A at 440 Hz with a click on every beat. One is a proper 48 kHz file, one a proper 44.1 kHz file, and one is the 48 kHz audio with a header that says 44.1:

mislabeled.wav: header says 44100 Hz, 2 ch, 24-bit PCM, 3.732 s
  strongest tone at the header rate: 404.3 Hz (-147 cents vs 440)

  fix: re-stamp the header to 48000 Hz (no resampling)

The 44.1 kHz loop is fine as a file. Its tone measures 440.0 Hz at its own rate. Unconverted in a 48 kHz session it plays at 152.38 BPM and 1.467 semitones sharp, and the fix is to convert it. The mislabeled one is different. Its header says 44.1, but the tone measures 404.3 Hz at that rate, 147 cents flat of where it should be. The header is the liar. Honoring it plays the loop at 128.62 BPM. The fix there is to re-stamp the header to 48 kHz without touching the audio. Convert it instead and you bake the wrong speed in for good.

Fixing it in the session

  1. Choose the project rate first. Pick it from where the song is going, 48 kHz for most video work, and set it before you import anything. Delivery rates are covered in sample rate and bit depth are delivery hygiene.
  2. Let the DAW convert on import. Look for an import option that converts the sample rate or matches the project, and turn it on.
  3. Convert folders before you use them. A mixed-rate pack is easier to batch-convert once with a good converter than to catch loop by loop.
  4. Match the interface. Make sure the audio device is running at the project rate.
  5. Mislabeled file? Re-stamp, don’t convert. If a known note measures about 1.47 semitones off, the header is wrong. Change the rate in the header and leave the samples alone.
  6. Check with your ears and a tuner. Put a tuner on a held note or the 808 tail. A whole loop that’s about 147 cents off is a rate problem. A few cents off is just tuning, as in tuning an 808 to the key of your song.

The accident is a real effect

Here’s the funny part. Playing audio slower so the pitch drops with it is the whole sound of a chopped-and-screwed slowdown. A mismatch is that effect without anyone choosing it: 0.91875x and 1.47 semitones down. If you want the drop, make it on purpose, at the amount you like, then do it properly to a fresh file. You can hear what that sounds like in the ScrewAI demo, and when to slow the bounce covers where it belongs in the workflow. Keep the session itself on one clock.

Genre notes

  • Hip-hop and sampling. Rips, crate digs and old loops come at every rate. Convert to the session rate before you chop, or every chop is 1.47 semitones off the key you set.
  • Content and video. Video timelines are commonly 48 kHz. Bounce the beat at the rate of the video project so it doesn’t drift.
  • Collaborations. Agree on one rate before anyone sends stems, and say it in the file names, as in exporting stems for a mixer.
  • High-rate sessions. 88.2 or 96 kHz files in a 44.1 or 48 kHz player come out around an octave low and half speed, so you’ll hear it at once. The near misses are the ones that hide.
Wrong clock, not wrong audio. Convert when the session doesn’t match the file. Re-stamp when the header is lying.
Why does my sample sound slower and lower in my DAW?
It was made at a higher sample rate than it’s being played at, and it isn’t being converted. A 48 kHz file at 44.1 kHz plays at 0.91875x speed and 1.47 semitones flat. Convert it to the project rate on import.
How many semitones is the difference between 44.1 and 48 kHz?
1.467 semitones, or 146.7 cents. The speed ratio is 1.08844 one way and 0.91875 the other, so a 140 BPM loop plays at 152.38 or 128.62 BPM.
Should I resample the file or change the sample rate in the header?
Resample (convert) when the header is right and your session runs at a different rate. Change the header when the header itself is wrong. Measure a note you know: if the whole file is about 147 cents off at its own rate, the header is wrong.
Why is my audio drifting out of sync with my video?
Often a sample-rate mismatch. Audio made at 48 kHz played as 44.1 kHz falls 5.31 seconds behind after one minute. Export at the video project’s rate and make sure the editor isn’t reinterpreting the file.
